# Динамические события карт в World of Tanks EU

## Область исследования

Исследование выполнено для World of Tanks EU 2.4.0.0 (#944). Клиент RU и
версия мода для RU в исследование и будущую реализацию динамических событий не
входят.

Проверка выполнялась на Himmelsdorf через локальный просмотрщик и WotStat REPL.
Исходники клиента использовались только для чтения; исходники клиента,
распакованные библиотеки и оригинальные ресурсы игры не изменялись.

## Краткий вывод

Динамическое событие не является полной заменой карты. В уже загруженном
пространстве присутствуют связанные CGF-prefab’ы и sequence-компоненты,
которые переключают обычные, переходные и разрушенные объекты карты.

Sequence можно произвольно прокручивать в обе стороны и фиксировать на паузе.
На проверенном событии переход к началу возвращает исходную геометрию, а
переход к конечному времени включает разрушенное состояние. Пересоздание
пространства для этого не требуется.

Нативная боевая цепочка клиента выглядит так:

```text
серверное событие → Visual Script/VSE → CGF sequence → объекты карты
```

WG описывает Random Events как изменения маршрутов, укрытий и объектов внутри
текущей карты, а не как выбор отдельной карты: [Random Events в обновлении
1.23](https://worldoftanks.eu/en/news/general-news/random-events-new-gen-maps/),
[разбор CGF/VSE-механики](https://worldoftanks.eu/en/news/general-news/random-events-how-it-works/).

## Himmelsdorf: две независимые группы

В пакете карты группы разделены каталогами ресурсов:

```text
content/CGFPrefabs/Map_scenarios/04_himmelsdorf/04_airship_crashing/
content/CGFPrefabs/Map_scenarios/04_himmelsdorf/04_train_crashing/
```

Их технические идентификаторы:

```text
04_airshipCrash01
04_trainCrash01
```

У каждой группы есть технический якорь `<event>_scenario` и связанные
объекты. Для первой группы в ресурсах присутствуют, среди прочего:

```text
04_airshipCrash01_airship_complete.prefab
04_airshipCrash01_crashingBuilding_01_complete.prefab
04_airshipCrash01_crashingWall_01_complete.prefab
04_airshipCrash01_scenario.prefab
```

Для второй группы:

```text
04_trainCrash01_train_complete.prefab
04_trainCrash01_scenario.prefab
```

Следовательно, это должны быть две отдельные записи состояния в просмотрщике.
Нельзя управлять только одним объектом, если событие состоит из нескольких
sequence-объектов: связанные sequence нужно переключать согласованно.

## Проверенная работа Sequence

Для `04_airshipCrash01_airship_complete.prefab` на текущем EU-клиенте:

```text
duration = 150.0 секунд
```

Проверенные позиции:

```text
0.8 → 120.0 секунд → Paused
0.5 →  75.0 секунд → Paused
0.1 →  15.0 секунд → Paused
```

Позиция задавалась через:

```python
sequence.pause()
sequence.requestTime(sequence.duration * position)
```

После следующего игрового тика фактическое `sequence.time` соответствовало
запрошенному значению. В просмотрщике переходы между 0.8, 0.5 и 0.1
проигрывались в обратном направлении без перезагрузки карты.

`requestTime()` — асинхронная операция. Контроллер должен учитывать, что
изменение применяется следующим тиком, и не считать вызов мгновенным
подтверждением состояния.

Sequence может содержать как плавные ключи трансформации, так и дискретные
переключения видимости/коллизий. Поэтому произвольная прокрутка хорошо подходит
для геометрии, движения и разрушения, но отдельные побочные эффекты — звук,
частицы, однократное создание prefab’ов — требуют осторожности. Во время
ручной прокрутки sequence следует держать на паузе.

## Как получать события без ручных названий

В `ArenaType` для карты доступны слои миникарты и общие настройки Random
Events, но отдельного локализованного имени события не найдено. В клиентском
коде `Avatar.onRandomEvent(eventName)` также получает технический идентификатор.

Для универсальной реализации следует извлекать события из текущих ресурсов и
загруженного CGF-пространства:

1. Найти объекты текущего `spaceID` с помощью `CGF.CommandQueue(spaceID).manager`.
2. Выделить технические якоря вида `<event>_scenario`.
3. Собрать связанные имена с суффиксами `complete`, `normal`, `transition`,
   `destroyed` и sequence-компоненты с тем же префиксом.
4. Использовать исходный технический идентификатор или путь ресурса как
   стабильный fallback для отображения.
5. Не интерпретировать имя самостоятельно и не зашивать в код слова вроде
   «поезд» или «дирижабль».

Пары слоёв `zone/destroyed` из `minimapLayers` полезны как дополнительный
признак и источник данных миникарты, но не должны быть единственным источником
3D-событий: несколько слоёв могут относиться к одной sequence-группе.

## Отличия локального просмотрщика от боя

`LocalSession` создаёт локальное `BigWorld`-пространство и подключает геометрию,
но не поднимает полноценные `Avatar`/`ClientArena` и серверную VSE-сессию.
`BigWorld.player()` в просмотрщике является `Account.PlayerAccount`.

Поэтому прямой вызов нативной цепочки
`VSE.passEventToVisualScript(...)` не является универсальным способом запуска
события в просмотрщике: отсутствуют боевой контекст, серверные параметры и
провайдер планов `ClientArena`.

Практическая точка интеграции — локальный адаптер над CGF sequence-объектами,
связанный с жизненным циклом `LocalSession`.

Нативные `Minimap Changer`, `Zone Marker` и `Zone with timer UI Notification`
в локальном просмотрщике также не запускаются автоматически: боевой
`MapZoneSystem` требует боевого контекста. Слои миникарты нужно будет отдельно
синхронизировать с локальным состоянием события.

`MapActivities` — это в основном автономные визуальные активности вроде
самолётов, взрывов и звуков. Они не заменяют структурные Random Events и не
должны автоматически смешиваться с контролем геометрии.

Геометрии с суффиксами `*_sm24` и `*_sm25` следует исключить из обычного
переключения: это полноценные сценарные варианты карт, а не состояния одного
динамического события.

## Стартовая точка для реализации

Рекомендуемая внутренняя модель события:

```text
DynamicEventDescriptor
  id                 технический идентификатор
  resourcePath       путь scenario/prefab, если доступен
  sequenceObjects    все связанные sequence-объекты
  duration           длительность или диапазон времени
  minimapLayers      связанные пары слоёв, если найдены
  currentTime        фактическое состояние после применения
  pendingTime        последнее запрошенное состояние
```

Базовые операции адаптера:

```text
discover(spaceID)
setTime(eventID, time)
pause(eventID)
reset(eventID)
stop()
```

`setTime` должен применять значение ко всем sequence одной группы и сохранять
последнее запрошенное значение до следующего тика. Если исходный корневой
объект помечен `SelfInactive`, его сначала нужно активировать через
`CGF.CommandQueue`; это актуально для `04_airshipCrash01_airship_complete`.

При остановке просмотра все изменённые объекты и созданные контроллером
ресурсы нужно вернуть/удалить до очистки space mapping. Подписки и callback’и
должны сниматься синхронно в `stopping`.

Первой проверенной реализацией целесообразно считать Himmelsdorf с двумя
техническими группами. Остальные карты следует добавлять через автоматическое
обнаружение и отдельную smoke-проверку sequence-групп, а не через общий список
семантически угаданных названий.
